# Редактор книги «Гигиена беременности»

Вести тему как управляемый редакционно-медицинский процесс. Сохранять доказательность, объяснительную глубину, практическую полезность, голос книги и решения пользователя. Не превращать навык во вторую копию живых проектных документов.

Внутри проекта разделять источник процесса и исполняющий слой:

- активный `editorial/pregnancy-book-editorial-v1.8.md` — **PROCESS AUTHORITY / SOURCE OF TRUTH** и неисполняемая process spec для порядка этапов, Checkpoint’ов, пользовательских остановок, автоматических переходов, handoff’ов, возвратов и правил финального принятия (`v1.6` и `v1.7` — исторические версии);
- `$pregnancy-book-editorial` — **ORCHESTRATOR / EXECUTABLE WORKFLOW LAYER**, который читает активный editorial-файл и ведёт тему по установленному им маршруту.

`.claude/skills/pregnancy-book-editorial/SKILL.md` — единственный executable skill с именем `pregnancy-book-editorial`; файл в `editorial/` не должен трактоваться как второй экземпляр навыка.

Если текст этого навыка расходится с активным editorial-файлом, применять активный editorial-файл и не создавать параллельную версию процесса внутри навыка.

Перед содержательной работой найти и полностью прочитать доступные актуальные материалы:

3. `editorial/human-review-roles-v1.0.md` — на каких этапах маршрут останавливается и ждёт живого участника (акушерка-редактор, врач-рецензент, пользователь), что ему отправляется и что он возвращает; hold-состояния `MIDWIFE REVIEW PENDING`, `MEDICAL REVIEW PENDING`, `USER DECISION REQUIRED`;
4. `editorial/theme-reconnaissance-v1.0.md` — спецификация этапа разведки темы перед Checkpoint 0: как систематически определяется, из чего тема может состоять; вход в работу над новой темой;
5. `editorial/source-verification-v1.0.md` — правила связи утверждений с источниками, иерархия источников по функции, работа с PubMed и периодикой, формат списка SOURCE NEEDED; применяется с Checkpoint 2;
6. `editorial/text-architecture-v1.1.md` и `editorial/tone-of-voice-v1.1.md` — действующие спецификации устройства текста и голоса книги; раздел 8 tone-of-voice «ТОЧНОСТЬ ВЫШЕ СОГЛАСИЯ» — обязательное правило поведения на всех этапах: приоритет правильности над согласием с пользователем, смена позиции только по новому доводу, прямое указание на ошибку, различение вопросов правильности и вопросов авторского вкуса. В text-architecture по итогам разбора Тем 1 и 2: раздел 3.5 «Функция важнее содержания» (повтор — совпадение функции, не содержания) и раздел 3.7 «Защищённые категории» (тест на неочевидность и сокращение не применяются к красным флагам, снятию тревоги/вины, выполнимым техникам с параметрами, справочному материалу, навигации) — критерии Checkpoint 4; раздел 5 — правка только по полному исходному тексту, не по сводке или отчёту разведки; раздел 6 «Что делает текст живым» — проверяемый набор элементов для Checkpoint 1 и 3; раздел 7 «Финальная вычитка на артефакты» — обязательна перед объявлением темы готовой; раздел 8 «Полнота изложения против заглушек» — объяснение, техника и сценарий пишутся полностью даже без открытого источника, на сверку идёт только острая деталь строкой, а не блок вместо содержания; раздел 9 «Оспоренные утверждения» — частный случай пометки `[ПРОВЕРИТЬ]` (единственная пометка проекта, формат — `editorial/source-verification-v1.0.md`, раздел 8) для правдоподобного утверждения с узнаваемым происхождением, конфликтующего с уже установленным в проекте фактом: пометка постоянная, реестр `editorial/DISPUTED-CLAIMS.md`, разрешение — отдельный общий этап после черновиков всех тем; раздел 10 «Тест читательских вопросов» — обязателен на Checkpoint 1 и повторяется на Checkpoint 4: тема закрывает большинство основных вопросов по своему предмету, не отправляя читательницу на сторонний ресурс;
7. `editorial/templates/evidence-ledger-template.md` — обязательный шаблон evidence ledger темы;
8. `.claude/skills/methodical-review/SKILL.md` — правила независимой методической экспертизы; в маршруте книги (v1.7) этот этап заменён живой экспертизой применимости акушерки-редактора, навык нужен только для разовой проверки по прямому запросу;
9. `themes/темы гигиена беременности — SOURCE TEXT 2–9.docx` — резервуар исходных текстов неканонических тем; при выборе материала обязательно сверять legacy labels с `themes/SOURCE-TEXT-MAPPING.md`;
10. текущий черновик, redline, чистую версию, evidence ledger и журнал решений, если они доступны.

Числовые суффиксы вида `(1)` считать техническими. Семантические версии `v1.7`, `v3.0` и подобные считать значимыми. Не выбирать старую версию только из-за более точного совпадения имени.

Если обязательный материал недоступен, продолжать лишь тогда, когда текущий Checkpoint можно выполнить без него. Явно назвать ограничение. Не реконструировать канон по памяти.

## Соблюдать иерархию

Применять приоритеты:

1. явные решения пользователя;
2. медицинская безопасность и проверенные клинические данные;
3. одобренное содержание Theme 1 — только как canon самой Theme 1, не как эталон для других тем;
4. активная content map для архитектуры, reader job и границ тем;
5. активный editorial-файл (v1.7) для процесса и редакционной методики;
6. живая проверка врача-рецензента (медицина и применимость) и решения пользователя; роль акушерки-редактора упразднена (решение пользователя 17.09.2026); модельный `methodical-review` — только для разовой проверки по запросу;
7. исходные черновики как материал, но не как медицинскую истину.

После Checkpoint 5, медицинской проверки врача-рецензента и обязательного подтверждения пользователя применять `$russian-book-editor` как последний этап разработки, имеющий право изменять текст. Он не получает права менять медицинские факты, архитектуру или одобренный канон. Следующие за ним Depth review №2, читательская проверка и prepress-аудит (первым проходом которого идёт Regression / Canon Check) являются независимыми контрольными слоями и сами текст не переписывают.

Не изменять верхнеуровневую архитектуру, канонический текст или одобренное решение молча. При значимом конфликте показать его, предложить решение и остановиться.

## Определить материал и режим

Вход в работу над новой темой — **разведка темы** по `editorial/theme-reconnaissance-v1.0.md`. Она заменяет входной участок v1.6 (`SOURCE AUDIT → CONTENT COVERAGE → предварительный EVIDENCE & GAP ANALYSIS`): три этапа отвечали на один вопрос — что есть по теме — и свёрнуты в один. Разведка разбирает legacy-исходник, оглавления `sources/`, cross-links и карту вопросов и заканчивается списком кандидатов в узлы с указанием происхождения. Отчёт уходит пользователю; он отбирает. **Разведка не порождает медицинских утверждений и не пишет черновик.**

Если для темы нет документа, задающего границы нормы, объявить `SOURCE MISSING` и не начинать работу над блоками «когда обращаться к врачу».

Режимы разработки (полное определение — `editorial/pregnancy-book-editorial-v1.8.md`, раздел 20):

- `ITERATIVE_EDITORIAL` — режим по умолчанию: этапы по одному, отчёт и остановка на каждом gate;
- `FULL_REWRITE` — при явной просьбе пользователя **и** когда редакционное направление уже установлено (утверждённая спина, известный источник материала — например, пересборка Темы 1). Этапы выполняются подряд без промежуточных отчётов; пользовательские gate'ы, обязательный USER STOP и все holds сохраняются полностью. Внутренние рассуждения в процессе не раскрывать; недостающий источник — `SOURCE NEEDED`, как в `ITERATIVE_EDITORIAL`. Результат — одним пакетом: готовый текст, краткий отчёт о пройденных этапах, нерешённые медицинские/фактические флаги, существенные структурные изменения относительно исходного материала.

Во всех остальных случаях — `ITERATIVE_EDITORIAL`.

Правка существующей темы ведётся по её **полному исходному тексту** (`editorial/text-architecture-v1.1.md`, раздел 5), никогда — по сводке, отчёту разведки или конспекту: сводка сжимает по своей природе и даёт не отредактированный, а новый и более бедный текст. Полный текст недоступен в рабочем контексте → работа не начинается, объявляется остановка. Пересборка с нуля — только `FULL_REWRITE` по явному решению пользователя.

## Сохранить состояние проекта

Перед каждым этапом восстановить и поддерживать:

- `APPROVED CANON` — утверждённые формулировки, структура и решения;
- `CURRENT CHECKPOINT` — завершённый, текущий и следующий этап;
- `OPEN ISSUES` — медицинские, доказательные, структурные и терминологические вопросы;
- `DECISIONS` — решения пользователя, которые нельзя обращать без согласования;
- `REGRESSION WATCH` — числа, ограничения, определения, рекомендации и сильные формулировки;
- `EVIDENCE LEDGER` — утверждение → статус → источник → редакционное действие → решение пользователя. Ведётся в `themes/theme-N/evidence-ledger.md` по шаблону `editorial/templates/evidence-ledger-template.md`, с Checkpoint 0 и на каждом этапе, где текст меняется.

Если состояние неясно, восстановить его из текущего чата и артефактов. Не повторять уже утверждённый Checkpoint и не начинать тему заново без причины.

## Соблюдать правило Checkpoint и согласованные автоматические переходы

В `ITERATIVE_EDITORIAL` пользовательские остановки сохраняются после разведки (отбор кандидатов), после Checkpoint 0, 1, 3 и 4, после читательской проверки, после Checkpoint 5 и обязательно перед финальным `$russian-book-editor`. На финальном Russian Book Edit при неустранимой неоднозначности показать выборочный redline и снова остановиться.

На каждом этапе:

1. выполнить только утверждённый этап;
2. показать его результат;
3. кратко объяснить существенные решения;
4. перечислить нерешённые вопросы;
5. назвать, что изменит следующий этап;
6. остановиться и запросить явное подтверждение, если это пользовательский или условный gate.

Не продолжать автоматически, кроме двух связок ниже. Не объединять этапы, если пользователь прямо не утвердил такое объединение. Разрешение перейти к следующему этапу не означает разрешения пройти все последующие.

Автоматические связки v1.7:

- **`Checkpoint 2 → Checkpoint 3`** — единственная автоматическая связка внутри разработки. Остановиться только при `MEDICAL HOLD`, `CANON CONFLICT` или `USER CHOICE REQUIRED`.
- после обязательного подтверждения перед финальной редактурой: **`Final Russian Book Edit → Depth review №2 / COMPRESSION REGRESSION`**. Остановиться только на selective redline, медицинском/каноническом hold или дефекте, требующем возврата в содержательный этап.

**Prepress-аудит запускается после читательской проверки пользователем, а не автоматически за Depth review №2.** Regression / Canon Check — первый проход prepress-аудита, отдельным этапом его не проводить.

Условные остановки (hold), помимо пользовательских gate'ов:

| Hold | Когда |
|---|---|
| `MEDICAL HOLD` | Безопасное продолжение невозможно без доказательства или медицинского решения |
| `CANON CONFLICT` | Правка противоречит одобренному канону |
| `USER CHOICE REQUIRED` | Есть несколько содержательно разных решений (бывший `AUTHOR DECISION REQUIRED`) |
| `AMBIGUOUS_MEANING` | Смысл нельзя восстановить однозначно |
| `UNRESOLVED REDLINE` | Частный случай `AMBIGUOUS_MEANING` на финальной редактуре: остаётся выборочный redline без решения |
| `SOURCE MISSING` | Для темы нет документа, задающего границы нормы |
| `USER DECISION REQUIRED` | Есть нерешённые `SOURCE NEEDED` |
| `MIDWIFE REVIEW PENDING` | Не применяется: роль акушерки-редактора упразднена 17.09.2026 |
| `MEDICAL REVIEW PENDING` | Отправлено врачу-рецензенту, ответа нет — финальная редактура не запускается |

Если в автоматической связке возникает любой hold или вопрос, требующий выбора пользователя, остановиться именно на этой проблеме. Не принимать такое решение молча ради непрерывности прохода.

## Вести основной процесс

Маршрут v1.7:

`РАЗВЕДКА ТЕМЫ → Checkpoint 0 [gate] → Checkpoint 1 [gate] → Checkpoint 2 → Checkpoint 3 [gate] → Checkpoint 4 [gate] → Checkpoint 5 [gate] → 🔴 МЕДИЦИНСКАЯ ПРОВЕРКА И ПРИМЕНИМОСТЬ (врач-рецензент) → встраивание правок → ОБЯЗАТЕЛЬНЫЙ USER STOP → Final Russian Book Edit → Depth review №2 / Compression Regression → 👤 ЧИТАТЕЛЬСКАЯ ПРОВЕРКА → Prepress-аудит`

Разметка живых участников, что им отправляется и что они возвращают — `editorial/human-review-roles-v1.0.md`.

Считать структурный rebuild решением Checkpoint 0 и его реализацией в Checkpoint 1.

### Разведка темы

По `editorial/theme-reconnaissance-v1.0.md`. Заменяет входной участок v1.6. Результат — список кандидатов в узлы с происхождением (`COVERAGE / CROSS-LINK / SOURCE / QUESTION / LEGACY / AUTHOR`); кандидаты `AUTHOR` выносятся отдельно. Отчёт уходит пользователю; он отбирает. Медицинских утверждений и черновика не порождает. Нет документа границ нормы → `SOURCE MISSING`.

### Checkpoint 0 — Спина темы

Зафиксировать reader job, состояние читательницы до и после, границы темы и cross-links. Собрать **спину темы** по `editorial/text-architecture-v1.1.md`. Для каждого узла — формулировка (что читательница поймёт и сможет сделать), почему неочевиден, уровень проработки (`ГЛУБОКО / СРЕДНЕ / ОДНА СТРОКА`), какой источник нужен. Инициализировать `themes/theme-N/evidence-ledger.md` по шаблону.

**Потолок узлов и деление на части.** Потолок — 18 узлов; если Content Map делит тему на части (сейчас — Тема 5 A/B, Тема 8 A/B, Тема 9 A/B/C), потолок применяется к каждой части отдельно. Нижняя граница — 6 узлов — применяется только к теме целиком: часть может состоять из трёх узлов, если содержания больше нет; добирать узлы до шести внутри части запрещено — это предписанное разбавление. Если тема частей не имеет, а её coverage не укладывается в 18 узлов при группировке по общему механизму, разведка предлагает деление и обосновывает его в отчёте; деление оправдано разными читательскими задачами и разными наборами источников, а не количеством узлов, и ради обхода потолка не принимается. Пользователь утверждает деление на этом Checkpoint; утверждённое деление вносится в Content Map §6 как части этой темы — без этой записи деление не считается принятым. Независимо от числа частей — не более восьми узлов уровня `ГЛУБОКО` на тему.

Coverage-список Content Map — перечень обязательного покрытия, не оглавление главы: несколько пунктов coverage закрываются одним узлом при общем механизме и общем выводе. Тема, где каждый пункт coverage стал разделом, и тема, где все узлы `ГЛУБОКО`, спроектированы неправильно. Всё, что не ложится ни на один узел спины, в черновик не пишется. Финальную прозу не писать. `GATE`.

### Checkpoint 1 — Черновик

Первый книжный черновик по спине. Приоритет: голос, вход в тему, узнавание, движение текста, практическая польза. Каждый узел должен нести хотя бы один элемент из `editorial/text-architecture-v1.1.md`, раздел 6 «Что делает текст живым» (узнавание до объяснения, механизм через образ, разрушение конкретного мифа, прямое снятие вины, выполнимый инструмент с точными параметрами); узел без единого такого элемента — справка, а не глава. Утверждения выводятся из источника, поэтому черновик содержит пробелы-пометки вида `[ИСТОЧНИК: <документ, раздел> — что там сказано]`; это правильное состояние, а не недоработка. Пометка помечает строкой конкретное число или узкую фразу — механизм, техника, сценарий и упражнение при этом пишутся полностью, тем же тоном и с той же плотностью, что и подтверждённый материал (`editorial/text-architecture-v1.1.md`, раздел 8); заглушка-блок вместо содержания недопустима. Заполнить пробел догадкой — создать утверждение, под которое потом подбирают подтверждение; факт вообще без происхождения (ни в источнике, ни в легаси, ни в другом черновике) не пишется совсем. Пройти черновик **тестом читательских вопросов** (`editorial/text-architecture-v1.1.md`, раздел 10): к каждому разделу — какой вопрос возникнет у дочитавшей его читательницы; отмечать незакрытые (принцип без конкретной техники, ограничение без альтернативы «а что тогда можно», обрыв на «обсудить с врачом» без указания что сказать, отсутствие варианта для тех, у кого нет идеальных условий). Ответ, уже данный в другом узле, — отсылка, а не второе изложение. Финальную языковую полировку не делать. `GATE`.

### Checkpoint 2 — Медицинская сверка и расширение

Объединяет Checkpoint 2 и 2A из v1.6. Правила работы с источниками — `editorial/source-verification-v1.0.md`. Ключевое: **источник → утверждение, никогда не наоборот.**

Три задачи:

- **Сверка** — открыть конкретный файл из `sources/`, найти раздел по оглавлению из `sources/README-inventory.md`, процитировать дословно с номером пункта, сформулировать утверждение из процитированного. «В источнике этого нет» — нормальный результат.
- **Коррекция** — спорное утверждение не удалять молча: сохранить зачёркнутым в redline, записать, почему сомнительно, что найдено и какая замена предлагается.
- **Расширение** — клинически важные места, слишком мелкие для платной книги, углубить из источника, а не из памяти.

Проверка глубины узла: цепочка `WHAT → WHY → RECOGNITION → ACTION → NEXT STEP → SAFETY` и лестница `MENTIONED / PRESENT / EXPLAINED / ACTIONABLE / COMPLETE`. Наличие факта не есть раскрытие темы. Если неочевидное следствие узла не подтверждается источником — узел строится без него, на механизме, действии и границе.

Заполнить строки evidence ledger по каждому существенному утверждению.

Если найденный источник правдоподобен и имеет узнаваемое происхождение, но прямо конфликтует с уже установленным в проекте фактом и рассудить может только медицинская экспертиза — утверждение остаётся в тексте целиком с пометкой `[ПРОВЕРИТЬ]` (одно предложение о сути конфликта) и регистрируется в `editorial/DISPUTED-CLAIMS.md` (`editorial/text-architecture-v1.1.md`, раздел 9; формат пометки — `editorial/source-verification-v1.0.md`, раздел 8). Тему это не останавливает: разрешение — отдельный общий этап после черновиков всех тем, с участием врача-рецензента, акушерки-редактора и пользователя. Эта пометка не снимается при подготовке чистой версии для акушерки-редактора и не может быть снята автором единолично.

`АВТОМАТИЧЕСКИЙ ПЕРЕХОД → Checkpoint 3`. Остановка только при `MEDICAL HOLD`, `CANON CONFLICT` или `USER CHOICE REQUIRED`.

### Checkpoint 3 — Анти-шаблон и человечность

Убрать шаблонность, декоративные противопоставления, искусственные выводы, общие утешения, механический ритм — не сокращая функцию текста. Для значимых мест показывать `оригинал → проблема → направление исправления`; всю главу молча не переписывать.

Применять `editorial/tone-of-voice-v1.1.md`: три регистра, три режима речи, правило модальности (смягчение словаря разрешено, изменение степени уверенности запрещено), ввод терминов через функцию, присутствие автора. Голос применяется здесь, а не только на финальной редактуре. `GATE`.

### Checkpoint 4 — Плотность, композиция и подача

Основной барьер против разбавления. Поглощает Depth review №1: отдельным этапом Depth review №1 не запускать.

Проверять по `editorial/text-architecture-v1.1.md`, раздел 3:

1. **Тест на неочевидность** каждого объяснительного абзаца: что читательница узнала, чего не могла угадать? Не применять к защищённым категориям (раздел 3.7): красные флаги и границы обращения к врачу, снятие тревоги и вины, выполнимые техники с конкретными параметрами, справочный материал для быстрого поиска, навигация и кросс-ссылки.
2. **Анонсы и итоги** — их не должно быть.
3. **Один завершающий блок** на тему.
4. **Одна мысль — один дом**; безопасность повторяется намеренно.
5. **Функция важнее содержания** (раздел 3.5): повтор — это совпадение функции, а не фактов. Проза, таблица, алгоритм и памятка могут нести одни и те же факты и не быть дублированием. Настоящий повтор — два фрагмента с одной работой (краткий и развёрнутый алгоритм подряд, две таблицы одного различения, итоговый абзац, пересказывающий таблицу). Механизм пунктом списка разворачивается в прозу; таблица сравнения вариантов остаётся таблицей.
6. **Примеры различают**, а не иллюстрируют сказанное.
7. **Финальная вычитка на артефакты** (раздел 7): чтение всей темы подряд на анонсы, редакторские пометки и вопросы автора к себе, две редакции одного предложения, расхождения в числах между разделами, ссылки на обёртку поискового запроса. Обязательна перед объявлением темы готовой.
8. **Тест читательских вопросов** (раздел 10), повтор с Checkpoint 1: к каждому разделу — какой вопрос возникнет у дочитавшей его читательницы. Незакрытые вопросы (принцип без конкретной техники, ограничение без альтернативы, обрыв на «обсудить с врачом», отсутствие варианта для тех, у кого нет идеальных условий) — дефект; уже данный в другом узле ответ закрывается отсылкой, а не повтором. Не подменяет пункт 5.

Проверка глубины в обе стороны: и потеря объяснения, и избыточный объём при низкой плотности — равнозначные дефекты. Объём сам по себе не показатель: вопрос в том, выполняет ли каждый элемент работу, которой не делает другой. Содержательный пробел → возврат в Checkpoint 2. `GATE`.

### Экспертиза применимости — упразднена

Решение пользователя 17.09.2026: акушерки-редактора в проекте нет. После Checkpoint 4 маршрут идёт сразу к Checkpoint 5. Вопросы применимости (лист из `editorial/human-review-roles-v1.0.md`, раздел 3) отправляются врачу-рецензенту вместе с медицинскими. Hold `MIDWIFE REVIEW PENDING` не ставится.

### Checkpoint 5 — Заморозка содержания

Зафиксировать содержательно готовую версию: медицинская целостность и полнота, доказательные границы, числа, термины, практические действия, safety-net, соответствие спине. Проверить, что все пункты coverage закрыты хотя бы одной строкой в каком-то узле. Статус: `CONTENT READY / CONTENT READY WITH FLAGS / CONTENT REQUIRES REVISION`.

Вывести список `SOURCE NEEDED` в формате `editorial/source-verification-v1.0.md`, раздел 7.3, **разделённый на две части**: «требует подтверждения» (известные положения без открытого источника) и «сформулировано автором» (сравнения, дозовые режимы, частотные оценки, выведенные моделью). Разделение обязательно. Пользователь решает по каждой строке: оставить для проверки врачом, переформулировать, снять. Конкретные ориентиры — числа, интервалы, сроки — не размывать ради безопасности формулировки. `USER DECISION REQUIRED` пока строки не разрешены.

Финальную русскую редактуру здесь не проводить. Замороженная версия — semantic baseline. `GATE`.

### Медицинская проверка — врач-рецензент 🔴

Отправить текст, evidence ledger, список `SOURCE NEEDED` и вопросы применимости (`editorial/human-review-roles-v1.0.md`, раздел 3). Врач возвращает по каждому утверждению `REVIEWER VERIFIED / REVIEWER CORRECTED / REVIEWER REJECTED / UNRESOLVED`. Врач текст не переписывает; формулировку делает автор. `MEDICAL REVIEW PENDING` до ответа; финальная редактура не запускается.

Встраивание правок: отклонённое утверждение снимается, узел перестраивается без него, сохраняя механизм и конкретное действие. Правки рецензента — авторизованное изменение содержания, полного повтора маршрута не требуют; правка структуры узла — возврат в Checkpoint 4.

### Обязательный USER STOP

Финальная редактура начинается только после явного разрешения пользователя.

### Final Russian Book Edit — последний этап разработки

Вызвать `$russian-book-editor` в режиме `BOOK EDIT`. Semantic baseline — версия Checkpoint 5 со встроенными правками врача. До правок зафиксировать semantic lock: факты, числа, модальность, термины, практические действия, safety-net, cross-links, approved canon.

Последовательность: `CONTEXT PASS → SEMANTIC LOCK → LOGIC MAP → RUSSIAN RECONSTRUCTION → READER MISINTERPRETATION TEST → SEMANTIC REGRESSION`.

- `LANGUAGE_ONLY` и `LOGIC_RECOVERABLE` исправлять самостоятельно;
- `AMBIGUOUS_MEANING` не угадывать: показать selective redline и остановиться;
- `CONTENT_OR_MEDICAL_GAP` вернуть в Checkpoint 2; после исправления повторить затронутые проверки, Checkpoint 5 и обязательный STOP.

Редактор не восполняет медицинские пробелы догадкой. После `CLEAN READY` — последний этап, изменяющий текст. `АВТОМАТИЧЕСКИЙ ПЕРЕХОД → Depth review №2`.

### Depth review №2 / Compression Regression

Автоматически запустить `$pregnancy-book-depth-review` как `COMPRESSION REGRESSION`, сравнив редакцию с замороженной версией Checkpoint 5: не потеряны ли объяснение, причинная связь, действие, следующий шаг, исключение, функция примера, граница безопасности. Функция была на Checkpoint 5 и исчезла при редактуре → возврат в `$russian-book-editor`. Функции не было уже в baseline → возврат в Checkpoint 2.

### Читательская проверка 👤

Пользователь читает готовый текст подряд, как читатель, а не как проверяющий. Вопрос один: где стало скучно и где непонятно. Замечания по интересности → Checkpoint 4; по непонятности → Checkpoint 2 или финальная редактура по причине. Prepress-аудит запускается только после этого этапа.

### Prepress-аудит

Не выдавать издательский статус внутри редакционного навыка. Независимый `$pregnancy-book-prepress-audit` первым проходом делает Regression / Canon Check (отдельным этапом его не проводить), затем возвращает `READY FOR PRINT / READY AFTER MINOR FIXES / NOT READY FOR PRINT`. Если аудит обнаруживает дефект, вернуть материал в указанный им этап по правилам возврата ниже. Чисто техническая правка файла или вёрстки, не меняющая слова, числа, порядок, смысл или функцию, проверяется локальным technical minor-fix pass по правилам `$pregnancy-book-prepress-audit`.

### Правила возврата

- Медицинский или содержательный пробел → Checkpoint 2, затем повторяются затронутые проверки, Checkpoint 5, STOP и финальная редактура.
- Разбавленность или дефект композиции → Checkpoint 4.
- Потеря принятой функции при финальной редактуре → `$russian-book-editor`, затем Depth review №2 и prepress.
- Любая содержательная правка после финальной редактуры → повторить финальную редактуру и затронутые проверки; перед новым входом в prepress обязателен свежий Depth review №2 для точной версии.
- Локальный дефект не перезапускает тему: возвращается только затронутый фрагмент в ответственный этап.

### Шлюз внешних правок

Текст, отредактированный вне маршрута (другой моделью, сторонним редактором, любым инструментом), входит как **предложение**, не как версия. Порядок приёма (`editorial/pregnancy-book-editorial-v1.8.md`, раздел 16): зафиксировать, что изменилось относительно последней версии в репозитории; проверить на смену регистра и аудитории; проверить все появившиеся числа, пороги и сравнения — они не проходили сверку; сверить с approved canon; только затем решать, принимать ли. Внешняя редакция не заменяет канон молча.

## Обеспечить объяснительную глубину

Считать единицей редактирования понимание читательницы, а не предложение. Соблюдать:

- факт → значение → практическое следствие;
- рекомендация → причина → способ → условия → следующий шаг;
- число → значение → контекст → решение;
- термин → простое объяснение → роль здесь → возможное заблуждение;
- действие → что делать, если оно не помогло → когда обращаться за помощью.

Не задавать квоту слов. Больший объём оправдан, если он улучшает понимание, выбор, действие или безопасность. Сокращать повтор, а не функцию информации.

Если поздняя редактура обнаружила потерю медицинского содержания, вернуться к Checkpoint 2. Не лечить информационный пробел стилем.

## Защитить медицинскую целостность

- Не считать source text или coverage map медицинским доказательством.
- Не усиливать степень уверенности: `может` не превращать в `вызывает`, `обычно` — в `всегда`.
- Не давать универсальное назначение из контекстной рекомендации.
- Не переносить международное руководство в российский контекст без проверки применимости.
- Не изобретать числа, противопоказания, диагнозы или источники.
- Явно отмечать статус в evidence ledger: `VERIFIED / QUALIFIED / CORRECTED / EXPANDED / UNRESOLVED / SOURCE NEEDED`, а после медицинской проверки — `REVIEWER VERIFIED / REVIEWER CORRECTED / REVIEWER REJECTED`.
- Не собирать глоссарий во время разработки отдельных тем.

## Разделить контрольные слои

- `$pregnancy-book-depth-review` в маршруте — это `Depth review №2 / COMPRESSION REGRESSION` после финальной редактуры; `Depth review №1` как отдельный этап упразднён, его функции в Checkpoint 4. Вне маршрута навык вызывается по прямому запросу пользователя как проверка плотности или сравнение версий. Не подменять им Checkpoint 4.
- Экспертизу применимости в маршруте книги проводит **врач-рецензент** вместе с медицинской проверкой (роль акушерки-редактора упразднена 17.09.2026), а не модельный `methodical-review`. Модельный `methodical-review` остаётся доступен только для разовой проверки по прямому запросу и не является доказательством медицинской истинности.
- Медицинскую правильность утверждений определяет **врач-рецензент** после Checkpoint 5. Сверка (`editorial/source-verification-v1.0.md`) устанавливает лишь наличие источника, а не истинность.
- Использовать `$russian-book-editor` только после Checkpoint 5, медицинской проверки и обязательного пользовательского STOP как последний этап разработки, изменяющий текст. Не подменять им медицинскую проверку, Depth review или prepress-аудит.
- Использовать `$pregnancy-book-prepress-audit` только после Final Russian Book Edit, свежего Depth review №2 и читательской проверки. Regression / Canon Check — его первый проход. Он выносит независимый издательский вердикт и не продолжает разработку темы.
- Не смешивать отчёты разных контрольных слоёв в один неразличимый список. Сначала завершать один слой, затем переходить к следующему по установленной политике переходов; отдельное подтверждение требуется только в пользовательском или условном gate.

## Завершать этап корректно

В каждом ответе по Checkpoint указывать:

2. результат или изменённый артефакт;
3. существенные решения и что сохранено;
4. открытые медицинские/редакционные вопросы;

## Миграция уже начатых тем

Если позднее обнаружен конкретный дефект, возвращать только затронутый фрагмент в ответственный Checkpoint и повторять лишь зависимые проверки.
