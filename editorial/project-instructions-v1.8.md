# ПРОЕКТ: «ГИГИЕНА БЕРЕМЕННОСТИ»

Это рабочее пространство для создания русскоязычной научно-популярной книги «Гигиена беременности» для беременных читательниц.

Рабочий язык — русский.

## 1. GITHUB-FIRST: ОСНОВНАЯ РАБОЧАЯ БАЗА

Репозиторий `9479797/gigiena-beremennosti` является **единственным постоянным SOURCE OF TRUTH проекта**.

Перед содержательной работой:

1. прочитай корневой `AGENTS.md`;
2. определи активные версии управляющих документов в репозитории;
3. прочитай только файлы, необходимые для текущей задачи;
4. восстанови состояние темы из репозитория, а не по памяти предыдущего чата;
5. не используй старую копию файла из ChatGPT Project или прошлого чата, если в репозитории существует более новая активная версия.

Файл, который пользователь прямо загрузил в текущий чат как новый материал, может быть текущим входом в работу. Если он расходится с репозиторием, не заменяй канон молча: установи, является ли файл новой версией, черновиком или внешним источником. После принятия результата постоянное состояние фиксируется в GitHub.

Файлы ChatGPT Project и вложения чатов не должны становиться параллельным постоянным хранилищем копий управляющих документов, themes или skills.

## 3. ПРИОРИТЕТЫ

При конфликте использовать следующий порядок:

1. явное актуальное решение пользователя;
2. медицинская безопасность и проверенные данные;
3. approved canon конкретной темы;
4. активная Content Map — для архитектуры и границ темы;

7. исходные тексты и черновики.

Не считать SOURCE TEXT, Content Map, ранее написанный текст или модельную память медицинским доказательством.

## 5. СОСТОЯНИЕ КАЖДОЙ ТЕМЫ

Для фактически начатой темы использовать папку:

`themes/theme-N/`

Не создавать пустые папки будущих тем заранее.

В `themes/theme-N/README.md` поддерживать компактное состояние темы:

- название темы;
- общий статус;
- `CURRENT CHECKPOINT`;
- последний утверждённый Checkpoint;
- текущий рабочий/утверждённый файл;
- `APPROVED CANON` / важные решения;
- `OPEN ISSUES` / holds;
- `REGRESSION WATCH` и evidence ledger — ссылками на соответствующие файлы, если они вынесены отдельно;
- следующий допустимый шаг;
- дату/commit последней значимой фиксации при необходимости.

README темы является навигацией и state record, а не второй копией текста главы.

## 6. СТАНДАРТНЫЕ КОМАНДЫ ПРОЕКТА

Команды — это короткий интерфейс к существующему workflow. Они **не создают новых пользовательских Checkpoint’ов и не отменяют уже согласованные автоматические переходы**.

Ясная русская формулировка с тем же смыслом может трактоваться как соответствующая команда. Например, «начинаем тему 5» эквивалентно `START THEME 5`.

### `START THEME N`

Использовать для фактического начала новой темы.

Команда означает:

1. загрузить `AGENTS.md`, эту инструкцию, активную process spec, Content Map и относящиеся к теме материалы;
2. определить Theme N по активной Content Map, а не по legacy-нумерации SOURCE TEXT;
3. найти релевантный исходный материал через `SOURCE-TEXT-MAPPING.md`;
4. проверить существующие `themes/theme-N/`, `research/theme-N/` и связанные sources;
5. если тема действительно начинается и `themes/theme-N/` отсутствует — инициализировать её созданием `themes/theme-N/README.md`; пустую папку не создавать;
6. выполнить разведку темы по `editorial/theme-reconnaissance-v1.0.md`. Материал любого типа — legacy-глава, бриф, конспект, outline — на разведке считается материалом. Не считать бриф готовой главой и не переходить от сырого текста к книжной переработке, минуя спину темы. Если для темы нет документа, задающего границы нормы, объявить `SOURCE MISSING`;
7. передать отчёт разведки пользователю и дождаться отбора кандидатов, затем перейти к Checkpoint 0:

`РАЗВЕДКА ТЕМЫ → отбор кандидатов пользователем → Checkpoint 0`;

8. остановиться на существующем пользовательском gate после Checkpoint 0.

Не спрашивать отдельное разрешение между входными этапами, если process spec не требует остановки и нет `MEDICAL HOLD`, `CANON CONFLICT`, `USER CHOICE REQUIRED` или другой предусмотренной блокировки.

### `CONTINUE THEME N`

Использовать для продолжения темы в новом или текущем чате.

Команда означает:

1. восстановить состояние темы прежде всего из GitHub: `themes/theme-N/README.md`, утверждённых файлов, decisions, evidence ledger, Regression Watch и связанных research-материалов;
2. определить последний завершённый/утверждённый Checkpoint и следующий допустимый шаг;
3. не повторять уже утверждённый Checkpoint без причины;
4. продолжить до следующего **реального пользовательского gate** или предусмотренного hold;
5. соблюдать все автоматические связки активной process spec.

На текущем процессе (v1.7) пользовательские gates сохраняются после Checkpoint 0, 1, 3 и 4, после Checkpoint 5 и обязательно перед Final Russian Book Edit. Между Checkpoint 4 и Checkpoint 5 маршрут проходит через живую экспертизу применимости акушерки-редактора (hold `MIDWIFE REVIEW PENDING`); между Checkpoint 5 и USER STOP — через медицинскую проверку врача-рецензента (hold `MEDICAL REVIEW PENDING`).

Единственная автоматическая связка внутри разработки — `Checkpoint 2 → Checkpoint 3`.

После обязательного разрешения перед финальной редактурой: `Final Russian Book Edit → Depth review №2 / COMPRESSION REGRESSION`. Далее — читательская проверка пользователем, и только после неё prepress-аудит (не автоматически за Depth review №2). Regression / Canon Check в v1.7 — первый проход prepress-аудита, а не отдельный этап.

Если сообщение пользователя одновременно одобряет текущий gate и просит продолжить, это считается достаточным подтверждением этого gate; повторно спрашивать то же разрешение не нужно.

### `STATUS THEME N`

Read-only команда.

Ничего не переписывать и не продвигать по workflow. Вернуть:

- общий статус темы;
- последний утверждённый Checkpoint;
- текущий Checkpoint;
- актуальный рабочий/утверждённый файл;
- открытые holds/issues;
- следующий допустимый шаг;
- требуется ли сейчас решение пользователя или следующий переход автоматический.

### `SAVE THEME N`

Зафиксировать в GitHub текущее **уже принятое** состояние темы:

- сохранить утверждённый артефакт в правильном месте;
- обновить `themes/theme-N/README.md`;
- не повышать статус черновика автоматически;
- не создавать лишние `final_final`-копии;
- зафиксировать изменение понятным Git commit.

Команда `SAVE THEME N` сама по себе не является новым Checkpoint и не разрешает содержательные изменения, которые пользователь ещё не принял.

### `SYNC PROJECT`

Проверить связность репозитория без разработки текста:

- активные версии и ссылки в `AGENTS.md`, README и `editorial/`;
- наличие устаревших ссылок;
- возможные дубли и потерянные пути после переносов файлов;
- валидность навыков в `.claude/skills/`: корректный frontmatter (`name` + `description`), совпадение `name` с именем папки, отсутствие битых внутренних ссылок;
- темы с неясным или несохранённым состоянием.

По умолчанию это read-only аудит. Ничего не удалять автоматически. Для безопасно лишнего файла использовать рекомендацию:

`PROJECT DUPLICATE SAFE TO REMOVE — <файл>`

## 7. CHECKPOINTS: НЕ ДОБАВЛЯТЬ ЛИШНИЕ ОДОБРЕНИЯ

Точный порядок Checkpoint’ов и возвратов определяется `editorial/pregnancy-book-editorial-v1.7.md`.

Команды проекта не должны превращать каждый технический шаг в вопрос пользователю.

Останавливайся:

- на пользовательских gates, явно заданных process spec;
- на обязательном STOP после Checkpoint 5;
- при `MEDICAL HOLD`;
- при `CANON CONFLICT`;
- при `USER CHOICE REQUIRED`;
- при неустранимой неоднозначности (`AMBIGUOUS_MEANING / UNRESOLVED REDLINE`);
- при `SOURCE MISSING`;
- при `USER DECISION REQUIRED`;
- при `MIDWIFE REVIEW PENDING`;
- при `MEDICAL REVIEW PENDING`;
- при иной блокировке, предусмотренной активной process spec.

Во всех остальных случаях используй согласованные автоматические переходы.

## 8. МЕДИЦИНСКИЕ И РЕДАКЦИОННЫЕ ГРАНИЦЫ

Не придумывать и не исправлять по общему знанию медицинские факты, дозы, пороги, противопоказания, степень доказательности или источники.

Не усиливать модальность: `может` не превращать в `вызывает`, `обычно` — в `всегда`.

Сохранять уровни проработки:

`MENTIONED → PRESENT → EXPLAINED → ACTIONABLE → COMPLETE`.

Наличие факта не равно объяснению. Наличие объяснения не равно практической применимости.

Не сокращать необходимую функцию медицинского объяснения ради краткости, ритма или «лёгкости текста».

`themes/theme-1/tema_1_final_canonical.docx` не переписывать и не сокращать без явного решения пользователя. То же правило относится к одобренным файлам тем 2–4.

### 8.1. СТИЛЕВОЙ ОРИЕНТИР

Для Final Russian Book Edit использовать `editorial/tone-of-voice-v1.1.md` (голос) и `editorial/text-architecture-v1.1.md` (устройство текста); `.claude/skills/russian-book-editor/references/canonical-style-guide-v1.0.md` применять как руководство по русскому языку, синтаксису и борьбе с канцеляритом.

## 9. ПОСЛЕ FINAL RUSSIAN BOOK EDIT

Final Russian Book Edit — последний development stage, которому разрешено менять текст в рамках активной process spec.

Любая последующая содержательная или текстовая правка должна пройти предусмотренный повторный контроль. Чисто техническая правка файла/вёрстки, не меняющая слова, числа, порядок, смысл или функцию информации, не считается содержательной переработкой.

## 10. ВЕРСИИ И ИЗМЕНЕНИЯ УПРАВЛЯЮЩИХ ДОКУМЕНТОВ

Исторические версии сохраняются в Git, но не должны управлять активной работой.

Не изменять одновременно архитектуру книги, editorial workflow, правила специализированных проверок и canon, если задача требует изменения только одного уровня.

Новая версия управляющего документа становится активной после явного решения пользователя и обновления ссылок проекта.

При следующем `SYNC PROJECT` проверить, что все активные указатели ведут на эту версию и что визуальные/справочные материалы не создают ложного впечатления об актуальной версии.
